# Changelog

All notable changes to Ace's Discord Bot are documented here, in
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) style. The version
in `package.json` is the source of truth for the current release — every
version below must match a `package.json` version, and the dashboard
`/version` page renders from this file.

## [1.16.4] - 2026-11-20

### Added
- Deleted messages now say who deleted them, and the member log stops showing "By: unknown" for actions the bot itself took (1.16.4). Two related "who did it" fixes. (1) The message-delete log gains a `**Deleted by:**` line, between Author and Channel: when a mod (or the bot, e.g. a purge) deletes someone else's message, it names the deleter from the MESSAGE_DELETE audit entry (executor, matched on the author and the entry's channel); a bulk delete names the deleter from the MESSAGE_BULK_DELETE entry instead (target = the channel); when the author deletes their own message Discord writes no audit entry at all, so no entry after a careful check is reported honestly as "the author (deleted their own message)" — never a bare 'unknown'. The token/password redaction, the bot-author guard, the message_logs database row, and the edited-message handler are all unchanged. (2) The "who did it" resolver is now a shared helper (`src/utils/resolveActor.js`, used by both the member log and the message-delete log) that fetches the audit log twice — once immediately, once ~1.5s later — with a 30s freshness window (was one fetch, <10s). That closes the race that put "By: unknown" on the bot's own autorole: a member joined at 1:27 PM, the bot added The Einherjar + The Loyal in one roles.add(), and the GuildMemberUpdate event fired before Discord had written the audit entry, so the single immediate fetch found nothing even though the entry's executor was the bot itself. Same race could hit timeouts. Bans, unbans, timeouts, and role changes keep their exact log formats and still fall back to 'unknown' when no entry ever appears; the resolver still needs View Audit Log and never throws. No slash command file changed, so no deploy is needed. Verified by `tmp/verify-1.16.4.js` (39/39 through the real handlers with mocked guild/audit-log/message objects: a role change names the bot executor when the entry appears only on the second fetch, and still falls back to 'unknown' when no entry ever appears; a delete names the mod from a MESSAGE_DELETE entry, names the bulk deleter from a MESSAGE_BULK_DELETE entry, says self-deleted when no entry exists after retry, and rejects entries for the wrong author or the wrong channel; the timeout path still resolves; the bot-author guard, token redaction, and edited-message handler are untouched; no slash command file references the helper) and `check-deploy.js` (38 top-level, 0 problems — unchanged). The 1.16.1 suite now passes 32/37 — its 5 failures are this release's intended changes: the helper moved out of memberLogEvents.js into the shared file, the freshness window is 30s instead of 10s (so an 11s-old entry now resolves instead of reading 'unknown'), and the scope check now also sees resolveActor.js + messageLog.js. Server needs `git pull` + bot restart (required — the change lives in the event handlers); no `npm run deploy` (no command definition changed), no `npm install`, no dashboard restart. After the restart, delete a message as a mod and check the mod-log entry names you, delete your own message and check it says you deleted it yourself, and the next join's autorole entry should name the bot instead of 'unknown'.

## [1.16.0] - 2026-11-16

### Fixed
- Music voice joins work again — @discordjs/voice upgraded from ^0.18.0 to ^0.19.2, which has DAVE end-to-end encryption built in and on by default (1.16.0). Root cause, proven by the 1.15.40 close-code logger: every /music join died with voice close code 4017, which Discord's docs define as "E2EE/DAVE protocol required — This channel requires a client supporting E2EE via the DAVE Protocol" — since March 2026 Discord requires DAVE on all non-stage voice calls, and 0.18.0 never declares DAVE support in Identify, so the gateway sends HELLO then closes the connection during Identify, before Ready, and UDP is never attempted (Staff Errors rows #64–#72 and #73–#82). That is why the network, router, DNS, and region were all ruled out correctly and none of them could fix it. Fix: 0.19.2 sends `max_dave_protocol_version` in Identify (DAVE on by default; `@snazzah/davey` 0.1.12 is a hard dependency and ships a prebuilt `@snazzah/davey-linux-x64-gnu` binary, so no native compilation on the server). No music code changes were needed — the bot's voice API usage (`joinVoiceChannel`, `createAudioPlayer`, `entersState`, `AudioPlayerStatus`, `StreamType`, `createAudioResource` in `src/utils/musicQueue.js` and `src/commands/music/`) is unchanged in 0.19.x, and the 1.15.40 close-code logger still hooks correctly (Networking still emits 'close' with the code, and the instance is still reachable as `connection.state.networking`). discord.js stays 14.22.1 — not bumped. The lockfile also dedupes `discord-api-types` 0.37.120 → 0.38.59 (the nested copies under the discord.js packages are gone; 0.19.2 requires the newer range) — a consequence of the voice upgrade, not a separate bump. Verified by `tmp/verify-1.16.0.js` (14/14, live: a local TLS WebSocket server playing the voice gateway captured the real Identify from the real 0.19.2 `Networking` class — `max_dave_protocol_version` is 1 with default options and 0 with `daveEncryption: false`; replaying the gateway's 4017 close proved the 1.15.40 close-code listener still receives the code; the real `musicQueue.js` loads under 0.19.2) and `check-deploy.js` (38 top-level, 269 flat, 0 problems — unchanged). The 1.15.40 suite (18/18), 1.15.22 voice-diagnostics suite (16/16), and full-stack 1.15.39 (21/21) all still pass. **Server needs a Node upgrade first — 0.19.2 requires Node >= 22.12.0 and the server runs Node 20.5.1, so `npm install` will refuse until Node is upgraded.** Then `git pull`, `npm install`, `npm start` (bot restart required); no `npm run deploy` (no command changed), no dashboard restart strictly needed (harmless if done). After the restart, run one /music join in #botspamtemp, then /music play a track — the bot should join and stay, and Staff Errors should show no new 4017 line. Caveats: the known 0.19.x receive-side DAVE issue (reconnect loops / no audio capture) does not apply here — the bot never receives audio (no `receiver` usage anywhere in `src/`), it only sends; and the canvas EBADENGINE warning (canvas wants Node >= 20.9.0) should clear with Node 22. If `git pull` conflicts on package.json/package-lock.json (seen before), run `git checkout -- package.json package-lock.json` then `git pull` again.

## [1.15.40] - 2026-11-16

### Fixed
- The voice WebSocket close code is now logged on every failed join, so the next /music join will say WHY the voice server closes the connection instead of only showing the 10s timeout (1.15.40). Live incident: /music join fails with "Could not join" (6th identical error in #botspamtemp, Nov 16 00:25 EST) — the 1.15.22 diagnostics proved the voice gateway sends HELLO (op 8) then closes the WebSocket while the bot is still Identifying, before Ready (op 2), so UDP is never attempted (Staff Errors rows #64–#72). Reading the installed @discordjs/voice 0.18.0 source (dist/index.js) pinned down why the code was invisible: Networking.onWsClose destroys the instance and emits 'close' WITH the code, and VoiceConnection.onNetworkingClose stores that code on the connection state ONLY for 4014 (Disconnected + closeCode) — every other code just flips the connection back to Signalling and the code is lost, which is why the stateChange stream shows connecting -> signalling and the timeout with no reason. Fix, all in `src/utils/musicQueue.js`: a new `describeVoiceCloseCode()` (lines 71–98) maps codes to human meanings, and a new `attachNetworkingCloseLogger()` (lines 106–117) is called from the existing connection `stateChange` handler (line 138) whenever a NEW Networking instance appears on the state — it attaches a one-time 'close' listener to that instance, which fires alongside the library's own `once` and logs `Voice WebSocket closed in #<channel> — close code <code> (<meaning>)` through the same errorLogger pipeline as the 1.15.20/1.15.22 voice diagnostics (warn level, guildId, commandName 'play', so it appears on the dashboard Staff Errors page like the existing voice rows). One listener per Networking instance by construction (the attach is guarded on `networking !== previousNetworking`): a rejoin creates a new instance and gets its own listener, and the old instance is destroyed without emitting 'close', so no listener leaks and no spurious line is logged on a normal teardown. The log line carries no token — a close code is just a number. No join behavior, timeout, or retry logic changed — diagnostics only. Verified by `tmp/verify-1.15.40.js` (18/18: the live 4006 incident replayed through the real musicQueue.js with a fake voice connection — exactly one close-code line with guild/channel/command context, warn level, no token, and the timeout row still logged after it; meaning table for 4004/1006/4014/4015 plus an unknown code; same instance across two stateChanges still logs once, a new instance on rejoin logs its own close, a stateChange with no close logs nothing; source check that the new block never reads a token value) and `check-deploy.js` (38 top-level, 269 flat, 0 problems — unchanged). ## [1.15.39] - 2026-11-16

### Fixed
- Reaction-role mappings can finally all be saved — the 9 missing Choose Your Path roles were blocked by the emoji column's collation (1.15.39). Root cause, verified on a real MariaDB 10.11 server against the exact schema (not guessed): `reaction_roles.emoji` was `utf8mb4_unicode_ci` (UCA 4.0), under which every emoji added after Unicode 4.0 has the SAME collation weight, so the UNIQUE KEY `(guild_id, message_id, emoji)` rejects a second emoji for the same message with ER_DUP_ENTRY 1062 even though the emoji is different — measured: `'💻' = '🟢' = '🔵' = '🍄' = '🎵' = '🔔'` under `utf8mb4_unicode_ci` (all distinct under `utf8mb4_bin`), and the 11-row bulk add against the exact table stored exactly rows 1 (💻) and 6 (▶️ — a pre-4.0 geometric shape with a real DUCET weight, so it compares different) and failed the other 9 with `ERROR 1062 (23000): Duplicate entry ... for key 'uq_reaction_role'`, the exact live pattern. This also explains why the 1.15.37/1.15.38 reproductions missed it: their mock DBs used exact string equality, which is what the JS-side checks do — only the MySQL unique key compares with the column collation. Fix: the column is migrated to `utf8mb4_bin` (exact-byte comparison) on startup via a new `ensureReactionRolesEmojiCollation()` in `src/utils/database.js` `runMigrations()` (checks `INFORMATION_SCHEMA.COLUMNS.COLLATION_NAME`, ALTERs only when it is not already `utf8mb4_bin`, idempotent, warns-only on failure), and `sql/schema.sql` now creates it as `utf8mb4_bin` for fresh installs; no SQL for Ace to run by hand unless the migration warns (see below). The 1.15.37 honest-reporting behavior is unchanged (a row is ok only if verifiably persisted; saved counts stay honest) and the 1.15.38 shared-read duplicate check, named rejections, and wrong-channel repair are untouched. Verified by `tmp/verify-1.15.39.js` (37/37: collation-faithful mock reproduces the live 2/9 split with the surfaced 1062 error and console log line, migration flips the collation on startup and is a no-op second time, post-fix bulk re-add of the 9 and bulk 11 from empty both save 11/11 with 11 buttons, exact-duplicate and role-change rejections, wrong-channel repair, same emoji on a different message, non-duplicate INSERT failure still 500s with the reason) and `tmp/fullstack-1.15.39.js` (21/21 through the real Express route: pre-migration single + bulk 9 fail with the surfaced 1062, the failed saves hit `INSERT INTO error_logs`, post-migration bulk saves all 9, list page shows all 11 role names with an "11 role(s)" header) and `check-deploy.js` (38 top-level, 269 flat, 0 problems — unchanged). ## [1.15.37] - 2026-11-15

### Fixed
- Bulk reaction-role add now verifies mappings actually persisted — it can no longer report success for rows that did not save (1.15.37). Live incident: an 11-mapping bulk add to the Choose Your Path embed reported "11 added" with every row ✅, but only 2 rows (💻 PC Warrior, ▶️ YouTube Creator — rows 1 and 6) were stored; Refresh re-applied only 2 buttons. Root cause, verified in code: `db.query()` in `src/utils/database.js` catches every error internally and returns null, so `insertMappingRow()` in `src/utils/reactionRoles.js` could never see an INSERT failure — its `ER_DUP_ENTRY` catch was dead code in production, and `addMappingsBatch()` marked rows `ok:true` even when the insert did not land. Same silent-swallow class as the 1.15.34 bulk-delete bug. Fix, all in `src/utils/reactionRoles.js`: `insertMappingRow()` now checks the OkPacket `affectedRows === 1` from the insert (mysql2's `execute` returns it and `db.query()` passes it through) and, on any other outcome, looks up what is actually stored for that (guild, message, emoji) and throws a clear error — 500 "could not be saved to the database — please try adding it again" when nothing is stored, 400 "already mapped" when it is; the single-add path shares `insertMappingRow`, so it is covered too. `addMappingsBatch()` now cross-checks after each refresh with `SELECT emoji FROM reaction_roles WHERE guild_id = ? AND message_id = ?` — a row is `ok:true` only if the refresh built a button for it and the stored read confirms it; a row missing from the stored read is marked failed ("did not save to the database") and an unreadable verification says "could not be confirmed", never `ok:true`. Good rows are never rolled back over a count mismatch — the failure is reported honestly instead. The bulk-add route's `saved` count is computed from the honest per-row results (`results.filter((r) => r.ok).length`), so it now equals the number of rows verifiably persisted. `sanitizeParams()` behavior from 1.15.34 is unchanged.
- The duplicate check and the stored list now read the same truth (1.15.37). After the incident, re-adding the 9 missing mappings failed with "0 added, 9 failed" — every row "That emoji is already mapped on this message." — while the stored list still showed only 2 mappings for that message.
